# Decisions
## Decision Log
- Use a local-first production hub so editable scenes and episode history remain usable without an external video platform connection.
- Use portable Markdown knowledge atoms to preserve sources and production concepts across agent tools; the wiki remains distinct from runtime private data.
- Keep a deterministic structural graph separate from semantic claims. The installed Graphify CLI has a smaller command surface than the current skill reference.
- Treat provider availability, actual invocation and publishing as separate evidence states. A scaffold is not proof that those integrations run.
- Use the host's installed Korean SAPI voice for the first verified narration path. Use its authenticated host bridge from Linux containers and keep bridge/voice failures explicit; local voice synthesis is not a hosted generative-video integration.
- Attach generated narration and review decisions only to their exact episode versions. Review additionally binds the render job, URL and SHA-256, so a later edit cannot inherit approval of an earlier output.
- Restrict uploaded media demuxers and protocols at decode/probe time. A DASH playlist disguised as MP4 can otherwise reference a file outside uploads despite a safe top-level path; executable regression tests exercise the escape and all 11 allowed formats.
- Use a distinct `HOST_AGENT_BRIDGE_URL` Compose override so host loopback configuration cannot redirect container traffic to itself.
- Migrate consistent read-only SQLite snapshots into new empty volumes with hash/identity checks and explicit non-root ownership. Preserve original data and failed outputs rather than resetting storage.
- Restore episode/workflow snapshots as new current versions with required optimistic concurrency; preserve identity, old snapshots and review records. Episode restoration returns to draft, and comparisons use stable IDs rather than array positions.
- Persist a client request ID and normalized request identity before provider submission; Developer REST additionally sends persisted `generationJobs.id` as `Idempotency-Key`. This header does not authorize automatic replay: ambiguous submission still requires provider-history inspection. Known provider IDs can resume polling/import without a new paid request.
- Keep generation import and atomic episode apply as distinct operations so stale edits preserve paid candidates. A confirmed full generation workflow invokes version-checked apply before render; retained/recovered outputs require explicit Apply to the intended surviving scene at the current version. Describe these paths separately rather than promising manual Apply for every workflow.
- Bound automatic polling to 30 minutes. Recovery resets the polling window, preserves the provider ID and checks transport/capacity. A changed transport must not reinterpret a request identifier.
- Keep vendor MCP OAuth, Developer REST credentials, official CLI account login and the project-owned MCP bridge distinct. A configured connection or model catalog is weaker evidence than a completed generation/import/apply receipt.
- Reuse the workflow inspector for the Studio CTA. Preserve the saved graph and create an unsaved `script(existing) -> storyboard -> generate -> render -> review` draft when needed, so merely opening generation cannot save, run, spend or replace edited scene content. Track the live selected scene by stable ID; reorders update its index and deletion blocks quoting/running.
- Quote exact model/prompt/parameters immediately before paid confirmation using the official REST estimate endpoint; if unavailable, require explicit no-quote acknowledgement. Pass quoted workflow/episode versions through optional run guards, rejecting stale 409 before creating a run, so cross-tab edits cannot silently change the consented input.
- Apply the white design to all seven existing views through the shared shell rather than introducing a second editor. Source design/API facts in `artifacts/white-studio-research.json`; keep configured status weaker than verified authentication/availability, and local fixtures weaker than live-provider proof. The 1.4.0 harness bundle remains immutable and unchanged.
- Keep personal workspace layout client-owned: presets, bounded numeric dimensions, pointer/keyboard resizing and named profiles persist in browser storage only, so layout changes never mutate server episode/workflow data. Native dialog overlays move the existing inspector, narration and assistant panels; assistant unsent drafts remain episode-scoped transient state while inspector edits remain scene-scoped.
These are the current implementation rationale and boundaries, not historical claims about unrecorded decisions.

## Production-workspace interview — 2026-10-24

**Status:** approved requirements with the A+B implementation and isolated runtime evidence now recorded in `artifacts/production-workspace-implementation/verification.json`. The exact pre-status-update text is preserved in `approved-contract-snapshot.json` beside it and matches the frozen plan's contract SHA-256. This remains the canonical product decision record; research/prototype receipts and real production authorization are separate. No live consent, paid generation, publication, deployment or Git authority is implied.

### User-confirmed direction

- Improve the UI through deep research, building on the existing Premiere-inspired workspace rather than creating a separate editor.
- Keep keyword research, source evidence, scenario/storyboard, template/workflow configuration, editing, optional generation, rendering, review and channel upload within one production project's workspace and context.
- Connect each node's role, inputs and results into the complete production. Make the process reusable when channels are added, with consistent node responsibilities, channel styling and production rules.
- One production project covers one finished video's topic selection through channel upload. A channel contains multiple independent production projects; each reuses a production template without inheriting another project's run identities, approval or upload receipt. This is a confirmed product boundary, not a requirement for a new database table.
- Operators may add/remove supported nodes, change their connections and use multiple nodes with the same supported role inside each production project. Instantiate an independently editable, versioned project workflow from the reusable template and retain its source template identity/version. Project changes must not edit the shared template or another project's graph/settings. Nodes are distinguished by unique identities, not by assuming their role type occurs once.
- The first target is the 확인해봄 channel. The accepted example is AI news for YouTube Shorts, 45 seconds, with a hook, three news items and a closing scene.
- Prefer authentic existing footage found by search and cleared for reuse. Use source clips with news cards/captions; Higgsfield is an optional supplement, never fabricated evidence of an actual event.
- If no suitable reuse-cleared source footage is available, keep the selected story and use a news/image card rather than replacing the story or automatically generating video. Prefer an original text-only card when no third-party image is cleared. Any third-party image, including article/RSS thumbnails or og:image, requires its own source/rights/attribution/hash evidence; appearing publicly is not permission. This fallback does not authorize a paid Higgsfield call.
- Review and approve a whole production candidate rather than requiring approval for each scene. Generation approval does not authorize channel upload or public posting.
- Project completion means public publication immediately after the owner's final approval, not only a private upload or scheduled release. This confirms product behavior, not authority to publish any current video. Use the official YouTube Data API with channel-bound OAuth; retain Studio as a manual handoff rather than extending browser automation.

### Historical engineering observations at interview time

- `docs/premiere-workspace.md` documents the existing sage/white shell, synchronized scene bin/monitor/inspector/timeline and eight application views. It explicitly excludes independent NLE tracks, arbitrary node execution and verified public posting.
- Scene templates and workflow definitions are separate reusable artifacts; episode edits, workflow runs, renders and exact-output reviews already have versioned identities. A new database table named `project` is not an agreed requirement.
- `server/workflows.mjs` line 56 allows only one node of each supported type, and line 523 selects one scene for generation. Episode-wide multi-scene generation is new engine work, not an existing whole-production capability.
- `server/validation.mjs` lines 222–228 require local uploaded media; `server/render.mjs` lines 139–143 already support trim offsets and verify render inputs. Searching for a remote video URL does not make it a renderable local asset. Footage search/import and license/attribution history are new work.
- `server/workflows.mjs` lines 566–578 currently allow a publish-node channel override and a first-channel fallback before opening a platform session. This is an observed cross-channel reuse risk, not a verified safe channel-binding contract. No runtime correction was made during the interview.
- Harness 1.5.0 verification passed with `node scripts/version-harness.mjs verify`. Its publish-stage contract distinguishes platform-session/queue staging from verified upload and public publication.

Publication implementation contract (new work):
- One final approval binds the owner, project/episode version, local render job/hash, intended channel, title, description, relevant metadata, rights/attribution evidence, made-for-kids audience decision, AI-use disclosure decision and intended final visibility `public`. Missing audience/rights decisions block approval; generation consent alone is insufficient. Any change to these approved inputs requires new approval.
- Request and verify OAuth scopes sufficient for insert, read-back and update; `youtube.upload` alone is not a documented `videos.update` scope. Bind the authorized channel after consent, protect tokens outside tracked files, and block on missing scope, revoked/expired tokens or destination mismatch. No fallback to another account/channel or Studio automation.
- Persist the upload intent and recovery identity before submission. Use resumable `videos.insert` with explicit `status.privacyStatus: private`, `status.selfDeclaredMadeForKids` and `status.containsSyntheticMedia`; no `publishAt` for the selected immediate-publication path.
- Use owner-authorized `videos.list` to verify the returned ID, `snippet.channelId`, successful processing, approved metadata, audience and disclosure before any public transition. Rights evidence must already be complete; Studio copyright Checks are not a substitute or a universally available Data API gate.
- Revalidate the approved manifest immediately before `videos.update` sets the same video's `privacyStatus` to public. Respect update-part replacement semantics and preserve approved mutable status fields; read back public visibility, channel, audience/disclosure and identity afterward. A successful transfer or update response alone is not public-completion evidence.
- On a known failed public transition retain the private video and report blocked. On an uncertain transport result read back the known remote ID before reporting state; if read-back is unavailable, report unknown rather than falsely private/public. Never restart `videos.insert`, discard the remote identity or create a duplicate video to recover publication.
- The selected workflow is not scheduled release. If scheduling is later approved, `publishAt` requires private visibility and a future approved time; a time that has passed must require fresh approval rather than silently becoming immediate publication.
- Google's external OAuth apps in Testing receive seven-day refresh tokens for non-profile scopes, including this upload integration. Surface expiry/reconsent and verification requirements; do not claim indefinite unattended operation from a configured client or one successful token exchange.
- Automated YouTube Studio file attachment/click/input/navigation is disabled in the cutover; only manual Studio handoff remains. The earlier browser automation was a Terms-of-Service risk, not the approved upload transport. Use the channel-bound OAuth/Data API publication service and exact final approval instead.
- Primary policy/API evidence: https://www.youtube.com/t/terms ; https://developers.google.com/identity/protocols/oauth2#expiration ; https://developers.google.com/youtube/data/reference/rest/v3/videos/insert ; https://developers.google.com/youtube/data/reference/rest/v3/videos/update .

Implementation decision for PW-04: use repeated scene-specific `generate` nodes, with one persisted job and stable idempotency identity per node/target scene or slot. Whole-candidate approval covers every selected node's exact input and cost; do not introduce a second bulk-node mechanism. The implemented engine extends the earlier single-role/single-scene path and preserves independent approved slot jobs, connected branch evidence and completed outputs on resume. Multiple-source collection can still occur inside one `news` node; repeating collection nodes is an additional composition choice, not its prerequisite. A dedicated fact-check stage is not a supported type, and graph roles do not automatically launch specialist agents.

Repeated-node implementation contract:
- Engineering bounds are 128 nodes and 256 edges, independent of the ten supported roles, with the separate 1 MiB request-body limit retained. The 60-scene/nine-shared-stage example needs 69 nodes and 127 edges. Boundary/byte/order tests and an actual 128-node/256-edge canvas fit/pan/last-node/save/reflow journey are exercised in the implementation receipt; this is not a general throughput or usability benchmark.
- Validate unique IDs, known endpoints, duplicate edges, self-edges, cycles and required connectivity. Same-type edges may be valid when acyclic. Derive deterministic execution order from actual edges, not role-type order or stored node-list order.
- Every node instance must satisfy its own upstream prerequisites. A review consumes its connected render candidate; publish consumes that candidate's matching approval. Missing or ambiguous required inputs fail instead of selecting the first node with a matching type.
- Partial execution and resume select exact node IDs only, including start-node selection and reused prerequisite evidence. Migrate affected callers to this identity contract; preserve workflow/episode/version guards and historical evidence.
- Paid-job identity and recovery are per node instance and bound scene. Cancellation, restart, failed persistence or repeated resume must recover the same job rather than resubmit, recharge or reapply blindly; uncertain identity blocks paid replay.
- The editable harness contract must be synchronized with the implemented engine and promoted as a new immutable version after verification. Never change `harness/versions/1.5.0`; a successful integrity check of that old bundle is not semantic evidence for the new graph contract.
